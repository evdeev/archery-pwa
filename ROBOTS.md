# ROBOTS.md

Этот файл описывает правила работы ИИ-ассистентов и разработчиков в репозитории `archery-pwa`.

## Главный принцип

Репозиторий ведётся аккуратно, с понятной историей изменений, ветками, pull request, changelog и релизами.

ИИ-ассистент не должен делать хаотичные правки напрямую в production-код без структуры, описания и проверки.

## Ветки

- `main` — production-ветка. Только стабильные изменения.
- `develop` — основная ветка разработки.
- `feature/*` — отдельные задачи и эксперименты.
- `fix/*` — исправления багов.
- `release/*` — подготовка релиза при необходимости.

Обычный поток:

```text
develop -> pull request -> main -> release
```

## Pull Request

Каждое заметное изменение должно идти через PR.

В PR нужно указывать:

- что изменено;
- зачем изменено;
- какие файлы затронуты;
- как проверить;
- есть ли влияние на данные пользователя, PWA, cache или GitHub Pages.

## Версионность

Проект использует Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

Например:

```text
0.1.0
```

Правила:

- `PATCH` — багфикс без изменения поведения и структуры данных.
- `MINOR` — новая функция без поломки совместимости.
- `MAJOR` — несовместимые изменения, миграции данных, крупная переработка архитектуры.

Пока проект в ранней стадии, используется ветка версий `0.x.x`.

## CHANGELOG

Все заметные изменения фиксируются в `CHANGELOG.md`.

Формат:

- `Added` — добавлено;
- `Changed` — изменено;
- `Fixed` — исправлено;
- `Removed` — удалено;
- `Security` — безопасность.

## Releases

Релизы создаются через GitHub Releases.

Для релиза нужно:

1. Обновить `package.json` version.
2. Обновить `CHANGELOG.md`.
3. Вмержить изменения в `main`.
4. Создать git tag формата `v0.1.0`.
5. Запушить tag.
6. GitHub Actions создаст release draft.

## Архитектурные правила

Проект — чистый PWA без тяжёлого frontend-фреймворка на старте.

Обязательные правила:

- не использовать runtime patching;
- не складывать giant inline JS в `index.html`;
- не смешивать экраны, сервисы и компоненты в одном файле;
- не писать бизнес-логику прямо в DOM-обработчиках;
- не ломать PWA-пути для GitHub Pages;
- не добавлять сборщик без отдельного решения;
- не добавлять зависимости без необходимости.

## Структура проекта

```text
src/
  app/          запуск приложения, shell, router
  components/   переиспользуемые UI-компоненты
  screens/      экраны приложения
  services/     storage, pwa, import/export, persistence
  domain/       модели, константы, бизнес-правила
  styles/       глобальные стили и design tokens

public/         manifest, service worker, icons
.github/        workflows, templates
```

## PWA-правила

Особое внимание:

- service worker должен быть предсказуемым;
- cache version нужно менять осознанно;
- нельзя ломать обновление приложения на iOS;
- все пути должны работать с `/archery-pwa/` на GitHub Pages;
- offline-first поведение должно быть документировано.

## Данные пользователя

Нельзя менять структуру данных без:

- описания изменения;
- миграции;
- записи в changelog;
- проверки импорта/экспорта.

## Стиль работы ИИ

ИИ должен:

- делать законченное изменение, а не фрагмент;
- сохранять компонентную структуру;
- не переписывать всё приложение без причины;
- при изменении поведения обновлять документацию;
- при изменении публичного поведения обновлять `CHANGELOG.md`;
- по возможности делать PR, а не молча пушить в `main`.

## Definition of Done

Изменение считается готовым, если:

- код лежит в правильных слоях;
- нет giant inline JS;
- приложение открывается как статический сайт;
- PWA-файлы не сломаны;
- `CHANGELOG.md` обновлён при заметном изменении;
- версия обновлена при релизе;
- PR содержит понятное описание.
